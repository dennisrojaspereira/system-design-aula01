O caso

Um link curto parece trivial.
Até 100 mil pessoas clicarem nele no mesmo segundo.

Encurta: uma startup fictícia. Começa com 1 dev e 1 servidor. Termina numa campanha de Black Friday em rede nacional.

• Storytelling da aula: vamos acompanhar o Encurta crescer. • Fase 1: MVP para uns poucos clientes. Fase 2: clientes de marketing. Fase 3: um link viral na TV. • Pergunta para a turma: o que pode quebrar num sistema que só faz um SELECT por chave? • Anotar as respostas no quadro e voltar a elas no fim.

• Já começamos com 2 réplicas: app stateless é barato e evita a discussão de 'ponto único' cedo demais. • O banco é o único estado. Guarde isso. • Cada redirect faz DUAS idas ao banco. A segunda (contar o clique) é a que vai doer. • No kit simulamos 10 ms de rede até o banco (DB_EXTRA_LATENCY_MS), como num banco gerenciado em outra zona.

03 · Arquitetura · MVP

Uma tabela, uma chave

CREATE TABLE links (
  code       VARCHAR(16) PRIMARY KEY,
  url        TEXT NOT NULL,
  created_at TIMESTAMPTZ DEFAULT now(),
  expires_at TIMESTAMPTZ,
  clicks     BIGINT DEFAULT 0
];

-- redirect: lookup pela chave
SELECT url FROM links WHERE code = $1;

code é a chave

O redirect é um lookup por chave primária: O(log n), sem joins.

clicks mora na linha

Guarde esta coluna. Num link viral, todo mundo disputa a mesma linha.

• Modelo mínimo: a chave de acesso É a chave primária. • Padrão de acesso puramente chave → valor. Isso vai pesar na escolha do banco (seção 05). • Pedir para a turma achar o problema escondido: o 'clicks' na mesma linha da URL. • Num link viral, milhares de UPDATE por segundo na MESMA linha = disputa de lock + 1 commit por clique.

Encurta quer curto, não enumerável e sem gargalo: aleatório de 7 ou faixas embaralhadas.

• Não existe melhor: existe o que combina com os requisitos (curto, não enumerável, sem colisão, sem gargalo). • Aleatório: simples e não enumerável; preço = tratar colisão com INSERT … ON CONFLICT e retry. • Hash: deduplica URL repetida (às vezes desejável, às vezes não: analytics por cliente). • Contador: zero colisão mas expõe volume e permite varredura. Snowflake: sem coordenação, mas longo. • Faixas: o melhor dos mundos quando combinadas com embaralhamento (próximo slide).

Paradoxo do aniversário

575 links

bastam para 50% de chance de colisão num espaço de 238 mil códigos (3 caracteres).

Com 7 caracteres e 6 bi de links: ≈ 5 milhões de colisões em 5 anos. Trate o conflito sempre.

• Fórmula: n ≈ √(2·N·ln 2). Para N = 62³ = 238.328 → ~575. • Colisões esperadas ≈ n²/2N. Com n = 6 bi e N = 3,5 tri → ~5 milhões. • Lição: 'espaço enorme' não dispensa tratamento de colisão; só torna o retry raro. • O Lab 2 mostra a curva subindo conforme a tabela enche.

06 · Cache

Cache-aside: 20% dos links, 80% dos cliques

App

recebe GET /código

Redis

1 · GET l:código → hit? responde

Postgres

2 · miss → SELECT
3 · SET no Redis com TTL

≈ 33 GB

cabem os links quentes em memória

• Cache-aside: a aplicação consulta o cache; no miss, busca no banco e preenche o cache. • Hit ratio depende da distribuição: com cauda longa (poucos links virais), passa de 90%. • TTL é a válvula de consistência: link editado/expirado pode ficar velho até o TTL vencer. • Pergunta: cachear o redirect na borda (CDN) também? Guardar para a escala global.

06 · Cache

Quando o cache vira problema

Stampede

A chave viral expira e todos vão ao banco ao mesmo tempo.

→ Single-flight; renovar antes de expirar.

TTL sincronizado

Chaves criadas juntas expiram juntas.

→ Jitter de ±20% no TTL.

Links inexistentes

Todo miss de código falso vai ao banco.

→ Cache negativo com TTL curto.

Redis fora

O banco recebe tudo de uma vez, com cache frio.

→ Timeouts curtos; degradar; aquecer aos poucos.

• Cache resolve latência e carga, mas cria quatro modos de falha novos. • Stampede é o clássico de Black Friday: o link da TV expira e o banco recebe 500 SELECTs iguais. • Cache negativo protege contra varredura/bots, mas um link recém-criado pode 'não existir' por 30 s. • Redis fora: no kit usamos timeout de 50 ms e fallback para o banco. O sistema fica lento, não cai.

07 · Analytics

Tire o clique do caminho crítico

App

XADD no stream

Stream

Redis Streams ou Kafka

Worker

agrega em lote

Postgres / OLAP

1 UPDATE por lote

Síncrono

1 UPDATE por clique, todos na mesma linha do link viral. O redirect espera o banco.

Assíncrono

1 UPDATE para centenas de cliques. O contador atrasa alguns segundos: consistência eventual.

• Separar caminho crítico (redirect) de caminho analítico (contagem). • O redirect só publica um evento (~0,1 ms no Redis). Quem grava é o worker, em lote. • Trade-off: contador atrasado e uma fila para operar (lag, reprocessamento, perda se o broker cair). • Em escala: Kafka particionado por código + ClickHouse/Druid para consultas analíticas (por país, por hora).
